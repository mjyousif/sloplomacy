# Data Models & Schemas

The Diplomacy 1901 Tactical Engine maintains synchronized data contracts between the Python FastAPI backend (using Pydantic v2 in `backend/domain/`: `board.py`, `orders.py`, `issues.py`, `game_state.py` and `requests.py`) and the TypeScript frontend (defined in `frontend/src/types/diplomacy.ts`).

---

## Core Enumerations

### `Power`
Represents the seven Great Powers in standard 1901 Diplomacy:
- `AUSTRIA`
- `ENGLAND`
- `FRANCE`
- `GERMANY`
- `ITALY`
- `RUSSIA`
- `TURKEY`

### `UnitType`
- `A`: Army (moves strictly via adjacent land/coastal provinces or maritime convoy chains).
- `F`: Fleet (moves along sea zones and designated coastal shorelines).

### `ProvinceType`
- `LAND`: Inaccessible to Fleets (e.g. `PAR`, `BUR`, `MOS`).
- `COAST`: Accessible to both Armies and Fleets. Some coastal provinces have split coasts.
- `SEA`: Accessible only to Fleets (e.g. `NTH`, `MAO`, `ION`).
- `IMPASSABLE`: Neutral un-traversable territory (`SWI` — Switzerland).

### `OrderType`
Supported order commands across all 3 game phases:
- `HOLD`: Unit remains stationary and defends its province (defense strength = 1).
- `MOVE`: Unit attempts to relocate into an adjacent province or via sea convoy.
- `SUPPORT`: Unit bolsters another unit's move or hold action.
- `CONVOY`: Fleet in a sea zone forms a transport bridge for an Army.
- `RETREAT`: Dislodged unit retreats to an adjacent unoccupied, uncontested province.
- `DISBAND`: Disbands a unit (required on retreat failure or SC deficit).
- `BUILD`: Recruits a new Army or Fleet in a vacant home supply center during Winter Adjustments.
- `WAIVE`: Concedes an available build quota during Winter Adjustments.

### `IssueSeverity`
- `error`: An illegal move under official Diplomacy rules. Reverts to `HOLD` on adjudication.
- `warning`: A legal order that causes tactical conflict (e.g., self-bounce, unmatched support, attacking own piece, unassigned unit).
- `info`: Non-blocking advisory notice.

## Primary Schemas

### 1. `Unit`
Represents a military piece on the game board.

| Field | Type | Description |
| :--- | :--- | :--- |
| `id` | `string` | Unique identifier (e.g. `"ENG_F_LON"`, `"FRA_A_PAR"`). Format: `{POWER}_{TYPE}_{PROV}`. |
| `power` | `Power` | Owning Great Power. |
| `unit_type` | `UnitType` | `'A'` or `'F'`. |
| `province` | `string` | 3-letter province abbreviation (e.g. `"LON"`, `"STP"`). |
| `coast` | `string?` | Optional coast identifier (`"NC"`, `"SC"`, `"EC"`). |
| `is_dislodged` | `boolean` | Flag set if the unit was defeated in combat and must retreat or disband. |
| `dislodged_by` | `string?` | Province origin of the attacking unit that dislodged this unit. |

---

### 2. `Order`
Represents an instruction issued to a unit.

| Field | Type | Description |
| :--- | :--- | :--- |
| `unit_id` | `string` | ID of the unit receiving this command (or build ID e.g. `"BUILD_FRANCE_PAR"`). |
| `power` | `Power` | Owning Great Power. |
| `unit_type` | `UnitType` | Army or Fleet. |
| `origin` | `string` | Current province of the unit. |
| `origin_coast` | `string?` | Current coast (if fleet on split coast). |
| `order_type` | `OrderType` | `'HOLD'`, `'MOVE'`, `'SUPPORT'`, `'CONVOY'`, `'RETREAT'`, `'DISBAND'`, `'BUILD'`, `'WAIVE'`. |
| `target` | `string?` | Destination province for `MOVE` / `RETREAT` / `BUILD`, or target of supported unit. |
| `target_coast` | `string?` | Specific destination coast for fleet moves (e.g., `"NC"` when moving to `STP`). |
| `aux_unit_origin` | `string?` | Origin province of the external unit being supported or convoyed. |
| `via_convoy` | `boolean` | Flag set when an Army move explicitly requests convoy routing across water. |
| `is_explicit` | `boolean` | True if the player manually assigned or confirmed the order. |

---

### 3. `ValidationIssue`
Diagnostic feedback generated by `engine/validator/`.

| Field | Type | Description |
| :--- | :--- | :--- |
| `id` | `string` | Deterministic issue key (e.g., `"self_bounce_BUR"`). |
| `severity` | `IssueSeverity` | `'error'`, `'warning'`, or `'info'`. |
| `code` | `IssueCode` | Diagnostic enum (e.g., `SELF_BOUNCE`, `UNMATCHED_SUPPORT`, `ILLEGAL_MOVE`). |
| `title` | `string` | Short human-readable headline. |
| `message` | `string` | Detailed strategic explanation and suggested correction. |
| `unit_ids` | `string[]` | List of unit IDs implicated in this issue. |
| `provinces` | `string[]` | Provinces to highlight on the tactical board. |
| `power` | `Power` | Great Power to whom this issue belongs. |

---

### 4. `OrderResolution`
Tactical outcome computed by `engine/adjudicator/` for each unit.

| Field | Type | Description |
| :--- | :--- | :--- |
| `unit_id` | `string` | ID of the evaluated unit. |
| `origin` | `string` | Origin province. |
| `order_type` | `OrderType` | Evaluated order type. |
| `target` | `string?` | Intended destination. |
| `succeeded` | `boolean` | True if the unit executed its order without bounce, cut, or dislodgement. |
| `bounced` | `boolean` | True if move failed due to standoff or superior resistance. |
| `cut` | `boolean` | True if support was broken by an enemy attack. |
| `dislodged` | `boolean` | True if forced to retreat by a superior attack force. |
| `dislodged_by` | `string?` | Origin province of the unit that dislodged this unit. |
| `attack_strength` | `number` | Calculated attack force (base 1 + valid supports). |
| `defense_strength` | `number` | Calculated hold or defense force (base 1 + valid supports). |
| `reason` | `string` | Explanatory narrative text detailing resolution. |

---

### 5. `GameState`
Complete server snapshot of a game session.

| Field | Type | Description |
| :--- | :--- | :--- |
| `game_id` | `string` | Unique session or match ID (e.g., `"proto_1901"`). |
| `season` | `string` | `'Spring'`, `'Fall'`, or `'Winter'`. |
| `year` | `number` | Game year (e.g., `1901`). |
| `phase` | `string` | `'Movement'`, `'Retreats'`, or `'Adjustments'`. |
| `scenario_id` | `string` | Scenario loaded (`'standard_1901'`, etc.). |
| `active_power` | `Power` | Selected power in a sandbox game. A multiplayer game is shared by all its players, so this does not identify any of them: each client uses its own claimed seat. |
| `units` | `Unit[]` | All military units on the board. |
| `orders` | `Record<string, Order>` | Map of `unit_id` to `Order`. |
| `ownership` | `Record<string, Power>` | Map of province code to owning Power: supply centers, plus land provinces that are not supply centers, claimed by the last power whose unit ended a movement or retreat phase there (map colour only, never counted as centers). |
| `finalized_powers` | `Power[]` | Nations that have locked in their orders for the turn. |
| `surrendered_powers`| `Power[]` | Nations operating under Civil Disorder due to concession. |
| `issues` | `ValidationIssue[]` | Active diagnostic errors and warnings. |
| `last_resolution` | `SimulationResult?` | Cached non-destructive simulation output. |
| `turn_history` | `string[]` | Historical log of turn outcomes. |
| `builds` | `Record<string, Any>?`| Build quotas and available home SCs during Winter Adjustments. |
| `retreats` | `Record<string, Any>?`| Valid retreat provinces per dislodged unit during Retreats. |
| `timer` | `PhaseTimer?` | The match clock. `null` until the host starts it, in sandboxes, and once a power has won. |
| `winner` | `Power?` | Set once a power has won. The clock stays on the deciding phase and no further turns resolve. |
| `unit_options` | `Record<string, UnitMoveOptions>` | Server-computed move, convoy and support options per unit ID (`direct_moves`, `active_convoys`, `potential_convoys`, `own_fleet_convoys`, `convoyable_armies`, `convoy_targets`, `valid_supports`). Rebuilt on every refresh, on load, and from masked orders in `sanitize_game_state_for_viewer`; excluded from Supabase persistence (`DERIVED_STATE_FIELDS`). |

### 6. `PhaseTimer`
The clock of a live multiplayer match. Times are absolute, so it survives a restart. The rules are in `backend/engine/phase_timer.py`.

| Field | Type | Description |
| :--- | :--- | :--- |
| `stage` | `TimerStage` | `'voting'`, `'running'`, or `'paused'`. |
| `deadline` | `number?` | Unix time the vote or phase ends. `null` while paused. Clients count down from `remaining_seconds` instead. |
| `minutes` | `number?` | Length the running phase was given. |
| `players` | `Power[]` | Who votes, readies up and extends: seated, not surrendered, still in the game. |
| `votes` | `Record<Power, TimerChoice>` | Votes cast, where `TimerChoice` is `'15'`, `'20'`, `'30'`, or `'pause'`. |
| `extend_requests` | `Power[]` | Who has asked for more time since it was last added. |
| `ready_powers` | `Power[]` | Who has readied up in a paused game. |
| `remaining_seconds` | `number?` | Computed when sent: time left, so that a wrong device clock cannot matter. |
| `extensions_needed` | `number` | Computed: 5 of 7, scaled up to `ceil(5n/7)` for `n` players. |

### 7. `TurnHistoryEntry` and `TurnRecord`
The turn selector's data, from `GET /api/history` and `GET /api/history/{index}`. Both live in `backend/domain/game_state.py` and `frontend/src/types/diplomacy.ts`.

`TurnHistoryEntry` names one resolved phase:

| Field | Type | Description |
| :--- | :--- | :--- |
| `index` | `number` | Position in the game's history, oldest first. A rollback or the 30-phase cap can move it, so the client finds a turn again by season, year and phase. |
| `season` | `string` | `'Spring'`, `'Fall'`, or `'Winter'`. |
| `year` | `number` | Game year. |
| `phase` | `string` | `'Movement'`, `'Retreats'`, or `'Adjustments'`. |

`TurnRecord` extends it with the phase as it began. Its orders are public, since the phase has resolved, so it holds every power's:

| Field | Type | Description |
| :--- | :--- | :--- |
| `units` | `Unit[]` | The board before the phase resolved. |
| `orders` | `Record<string, Order>` | Every power's orders for the phase. |
| `ownership` | `Record<string, Power>` | Supply centre owners before the phase resolved. |
| `builds` | `Record<string, Any>?` | Build quotas, for an Adjustments phase. |
| `retreats` | `Record<string, Any>?` | Retreat options, for a Retreats phase. |
| `resolution` | `SimulationResult` | How each order resolved (succeeded, bounced, cut, dislodged). |

## Lobby & Multiplayer Schemas

### `MultiplayerGameSummary`
Summarizes an open lobby, active game, or saved sandbox in the match browser.

```typescript
interface MultiplayerGameSummary {
  game_id: string;
  name: string;
  status: 'waiting' | 'active' | 'completed' | string;
  season: string;
  year: number;
  phase: string;
  created_by?: string;
  creator_id?: string | null;
  created_at: string;
  last_moved_at?: string | null; // when a phase last resolved; null until one does
  participants: Record<string, GameParticipant>;
  finalized_powers: Power[];
  surrendered_powers?: Power[];
  is_sandbox: boolean;
  is_draft?: boolean;
  is_private?: boolean;
  has_passcode?: boolean;
}
```

*Note on `is_draft`*: Ephemeral personal solo sandbox sessions created via `POST /api/games/solo-sandbox` set `is_draft: true`. Draft sandboxes are hidden from public lobby listings and `/ws/lobby` WebSocket feeds to preserve player isolation, and can be promoted to permanent saved sandboxes (`is_draft: false`) via `POST /api/games/save-sandbox`.

*Note on `last_moved_at`*: `_execute_adjudication` sets it each time a phase resolves. It is saved inside the summary in `game_state`, so it needs no column.

*Note on `created_by` and `PROFILE_NAMES`*: `created_by` defaults to `""` and is stripped for UUID creators when persisting to Supabase so creator emails are never stored in `summary` or `game_state.summary`. On read and viewer sanitization, `PROFILE_NAMES[creator_id]` (from `public.profiles`) is authoritative; if `PROFILE_NAMES` is unavailable, `public_host_name` falls back to non-email `created_by` or `"Unknown host"`, and participant `display_name` falls back to `"Envoy"`.

### `LobbyGameRow` and `LobbyBrowsePage`
One public match in `GET /api/games/browse`, and a page of them. A row names players by display name only, never by email or user id.

```typescript
interface LobbyGameRow {
  game_id: string;
  name: string;
  status: 'waiting' | 'active' | 'completed' | string;
  season: string;
  year: number;
  phase: string;
  host_name: string;
  created_at: string;
  last_moved_at: string; // created_at until a phase has resolved
  claimed_powers: Power[];
  open_powers: Power[];
}

interface LobbyBrowsePage {
  games: LobbyGameRow[];
  total: number;
  page: number;
  page_size: number;
}
```

### `GameParticipant`
Represents an enrolled player commanding a nation in a multiplayer match.

```typescript
interface GameParticipant {
  user_id: string;
  email: string;
  display_name: string;
  power: Power;
  joined_at: string;
  surrendered?: boolean;
  surrendered_at?: string | null;
}
```

### Request Models:
- `CreateGameRequest`: `{ name, creator_power, user_id, email, display_name?, is_private?, passcode? }`
- `JoinGameRequest`: `{ power, user_id, email, display_name?, passcode? }`
- `LeaveGameRequest`: `{ user_id, email?, power? }`
- `SurrenderRequest`: `{ power, user_id, email?, leave: boolean }`
- `SaveSandboxRequest`: `{ name, user_id, email, display_name? }`
- `GenerateAIOrdersRequest`: `{ powers?: Power[] | null, include_active?: boolean }`
- `SingleOrderUpdateRequest`: `{ order, active_power?, turn? }`
- `FinalizeRequest`: `{ power, force?, turn? }`
- `TimerVoteRequest`: `{ power, choice: TimerChoice }`
- `TimerToggleRequest`: `{ power, active?: boolean }`
- `ScenarioRequest`: `{ scenario_id, active_power? }`
- `SeedScenarioRequest`: `{ scenario_id, game_id?, active_power? }`

## Authentication & Identity Schemas

### `AuthUser`
Represents an authenticated Supabase user whose token signature has been cryptographically validated:

```typescript
interface AuthUser {
  id: string;
  email: string;
  displayName: string;
  isLocalDemo?: boolean;
}
```

Backend (`backend/domain/requests.py`, returned by `security/auth.py`):
```python
class AuthUser(BaseModel):
    user_id: str
    email: Optional[str] = None
    is_authenticated: bool = True
```

### `DisplayPrefs`
A player's own map display choice. It's frontend only, so it has no counterpart in `backend/domain/`. It's stored in `localStorage` and in Supabase `user_metadata.display_prefs`, and is defined in `frontend/src/utils/displayPrefs.ts`:

```typescript
type PieceStyle = 'classic' | 'seated' | 'compact' | 'flags' | 'nameplate';
type UnitMark = 'icons' | 'vehicles' | 'nato' | 'letters';

interface DisplayPrefs {
  pieceStyle: PieceStyle;
  unitMark: UnitMark;
}
```

## Administrator Schemas

Used by the match creator to arbitrate games and perform scenario testing. In multiplayer games, all mutating admin actions require cryptographic Supabase JWT verification (`Authorization: Bearer <token>`):

- `AdminStatusResponse`: `{ is_creator, can_rollback, history_count, creator_email, creator_id }`
- `AdminRollbackRequest`: `{ user_id?, email? }` *(Identity verified via JWT Bearer token)*
- `AdminSetTurnRequest`: `{ season, year, phase, user_id?, email? }`
- `AdminMoveUnitRequest`: `{ unit_id, new_province, new_coast?, user_id?, email? }`
- `AdminSpawnUnitRequest`: `{ power, unit_type, province, coast?, user_id?, email? }`
- `AdminDestroyUnitRequest`: `{ unit_id, user_id?, email? }`
- `AdminSetOwnershipRequest`: `{ province, power?, user_id?, email? }`

## Real-Time WebSocket Synchronization Schemas

### `WebSocketGameUpdate`
Broadcast to connected clients on `/ws/games/{game_id}` whenever orders, finalizations, phase advancements, or player roster changes occur.

```typescript
interface WebSocketGameUpdate {
  type: 'game_update';
  game_id: string;
  state: GameState;
  summary: MultiplayerGameSummary | null;
}
```

### `WebSocketLobbyUpdate`
Broadcast to connected clients on `/ws/lobby` whenever a game is created, updated, joined, vacated, or its status changes. It lists public matches only.

```typescript
interface WebSocketLobbyUpdate {
  type: 'lobby_update';
  games: MultiplayerGameSummary[];
}
```
